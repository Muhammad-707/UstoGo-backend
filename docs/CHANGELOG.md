## [Unreleased]

### Added
- **Observability/security hardening pass (2026-08-05)**: `RedisHealthIndicator` on `/health/ready` (rate limiting and both Socket.io namespaces hard-depend on Redis; readiness never checked it); `helmet()`/`compression()` in `main.ts`; Sentry wired end to end (`SENTRY_DSN` had been validated since Phase 1 but nothing ever called `Sentry.init` — `GlobalExceptionFilter` now reports every 5xx via `captureException()`, never a 4xx).

### Fixed
- **`search_vector` migration-drift footgun (2026-08-05)**: `master_profiles.search_vector` declared `Unsupported("tsvector")` with a `dbgenerated()` default matching Postgres' actual generation expression, and both its GIN indexes given matching `map` names — `prisma migrate diff` against production now produces an empty migration instead of proposing to drop the column and its indexes on every unrelated `prisma migrate dev`, as it had at least three times since F-12.
- **Broken Docker build (2026-08-05)**: a pre-existing lockfile inconsistency in a transitive devDependency chain (`unrs-resolver`'s optional wasm32-wasi fallback, via `@napi-rs/wasm-runtime`'s `@emnapi/*` peers) made `npm ci` fail unpredictably depending on which platform last wrote `package-lock.json`. Surfaced when these commits' `package.json` changes invalidated Render's cached build layer. `Dockerfile` now uses `npm install` in both stages.
- **P0 — WhatsApp contact (2026-08-03, `MASTER_PROMPT.md`)**. The whole point of the marketplace is a direct WhatsApp line: a master's registration phone is adopted as the initial `whatsapp_phone`; `PATCH /users/me` can change it (E.164-only, `MaxLength(20)`, once per 24 h via `whatsapp_changed_at` — early retries get `422 WHATSAPP_CHANGE_COOLDOWN`, resubmitting the same number is a no-op that neither stamps nor trips the cooldown) and toggle `whatsapp_enabled` (defaults on). The number is published on `MasterPublicResponseDto.whatsappPhone` **only while enabled** — withheld otherwise, so a master who turns it off is immediately invisible to clients — always present on the admin masters listing, and included on booking detail for that booking's own client only (`BookingResponseDto.masterWhatsappEnabled`/`masterWhatsappPhone`). `POST /bookings/:id/whatsapp-click` (client-owner only, 404 for a foreign booking, never 403) records the first click in `whatsapp_link_clicked_at` — idempotent, so repeat clicks are free. All 15 demo masters carry realistic `+992…` numbers in the seed. 1046 tests total (832 unit + 214 e2e).
- **Master portfolio/gallery (B-45)**. Masters can showcase work photos on their public profile: `PortfolioImage` model (`caption`, `sortOrder`, soft-deletable), a new `PORTFOLIO_IMAGE` file purpose (5 MB, images only), and `GET/POST /masters/me/portfolio`, `PUT /masters/me/portfolio/order`, `DELETE /masters/me/portfolio/:imageId` — the same confirmed-file-ownership pattern `Certificate` already uses via `FilesService.getAttachable`. Capped at 20 images per master (`PORTFOLIO_LIMIT_EXCEEDED`, 422) so the public profile projection (`MasterPublicResponseDto.portfolioImageFileIds`) stays bounded without a second paginated endpoint.
- **Favorites**. Clients can save/unsave masters (`POST`/`DELETE /favorites/:masterId`, idempotent) and list their saved masters (`GET /favorites`) via the same public `MasterPublicResponseDto` projection search uses.
- **`GET /admin/masters`** (API.md §12, documented since F-04 but never implemented). Lists every master regardless of approval/active state — unlike public search, which only ever returns approved and active ones — filterable by `approvalStatus`, `status` (active/deactivated), `cityId`, `categoryId` and `search` (display name or account email), paginated the same way as every other list endpoint. `AdminMasterListItemResponseDto` is a distinct, admin-only projection: it includes `email`/`phone`, which `MasterPublicResponseDto` deliberately never exposes.

### Database
- **WhatsApp contact columns** (P0, `20260803210000_add_whatsapp_contact`): `master_profiles.whatsapp_phone` (`VARCHAR(20)`, nullable), `master_profiles.whatsapp_enabled` (`BOOLEAN NOT NULL DEFAULT true`), `master_profiles.whatsapp_changed_at` (`TIMESTAMPTZ(3)`, nullable), `bookings.whatsapp_link_clicked_at` (`TIMESTAMPTZ(3)`, nullable). Purely additive — nothing dropped. Already applied to the deployed Render/Neon database.
- **Search performance pass** (F-08 hot path, `k6/search.js`). Four additive indexes — nothing dropped, so no existing query can regress: `(approvalStatus, isActive, createdAt DESC)` and `(approvalStatus, isActive, ratingAverage DESC)` composite sort indexes, an `(approvalStatus, isActive, deletedAt)` covering index for the pagination count, and a GIN trigram index on `displayName` for the admin masters listing's `ILIKE` search. `SearchService.search` now runs the candidate-id query and the count in parallel (`Promise.all`) instead of one `COUNT(*) OVER()` query that scanned every matching row on every request — measured against a 50,000-master seed: data query 39ms → 0.2ms, count 16ms → 6.1ms, admin `ILIKE` from sequential scan → 0.5ms. API shape, ordering and totals are unchanged.

### Security
- No external penetration test has been performed against this codebase. `SECURITY.md`'s OWASP API Top-10 mapping and the internal threat model are the only security review this release has had.

### Added
- **Backup restore rehearsal and production runbook** (Phase 6). `scripts/backup-restore-rehearsal.sh` (`npm run backup:rehearse`) dumps the running Postgres container, restores into a throwaway database on the same instance, and verifies row counts on six tables match — run once locally, 2 seconds, every table matched; the mechanism is proven, the production-scale timing is what the quarterly rehearsal against a real backup measures. `DEPLOYMENT.md` §11's runbook gained two incident scenarios (2FA lockout via direct SQL — no API bypass exists by design; a stuck `Idempotency-Key`) and a new On-Call Rotation section documenting the escalation path; the named weekly schedule is left for the team to fill in, not something a repository can generate.
- **RS256 migration for access tokens** (Phase 6). `JWT_ACCESS_SECRET` (HS256, one shared secret) is replaced by `JWT_ACCESS_PRIVATE_KEY`/`JWT_ACCESS_PUBLIC_KEY` (base64 PKCS8/SPKI PEM, validated at boot by decoding and checking for real PEM markers). `JwtModule` signs with the private key; `JwtStrategy` and `ChatGateway`'s socket handshake both verify with the public key alone and pin `algorithms: ['RS256']` explicitly, closing the algorithm-confusion class of bug. `JWT_REFRESH_SECRET` is untouched — refresh tokens are opaque and database-backed, never JWTs. 914 tests total (706 unit + 208 e2e).
- **Personal data export and anonymised deletion** (Phase 6, v1 scope of `BACKLOG.md` B-70). `GET /users/me/export` returns the caller's own account/profile, bookings, reviews and notifications as JSON, read directly across modules the way `AdminModule`'s dashboard already does. `DELETE /users/me` now anonymises rather than only soft-deleting: email becomes a deterministic `deleted-<id>@deleted.invalid` placeholder (kept `NOT NULL`), phone/first name/last name/address/bio are overwritten, and the avatar is released the same way a replaced one already was. This is also what makes a deleted author display as "Deleted User" (BR-5) — a consequence of the overwrite, not a separate redaction step. 913 tests total (705 unit + 208 e2e).
- **Idempotency keys on mutating endpoints** (Phase 6). `IdempotencyInterceptor`, registered globally in a new `IdempotencyModule`, follows `AuditInterceptor`'s own precedent: a no-op for any route without `@Idempotent()`. A new `IdempotencyKey` model (unique on `(userId, key)`) means two concurrent requests with the same key race on the row *insert*, not on the handler; a genuine retry (same key, method, path and body — fingerprinted with a SHA-256 `requestHash`) replays the original response verbatim, a key reused for a different request gets `409 IDEMPOTENCY_KEY_REUSED`, and a key whose original request is still running gets `409 IDEMPOTENCY_KEY_IN_PROGRESS`. Applied to `POST /bookings` and `POST /admin/notifications/broadcast` — the two mutating endpoints with the clearest retry-duplication risk and no existing safeguard against it; more routes can adopt `@Idempotent()` without further plumbing. 902 tests total (697 unit + 205 e2e).
- **Device/session list with per-device revocation** (Phase 6). No new model — `RefreshToken.deviceId`/`userAgent`/`ipAddress` (DATABASE.md §4.1, collected since Phase 1) are folded by `TokenService.listSessions` into one entry per refresh-token family, since a family — not a single row — is what a rotating session actually is. `GET /auth/sessions` lists active devices most-recently-active first with a `current` flag; `DELETE /auth/sessions/:id` revokes one, `404 SESSION_NOT_FOUND` for an unknown or another account's family, following the ownership → 404 convention. Revoking the caller's own current session is allowed and behaves like `POST /auth/logout` for that device. 880 tests total (678 unit + 202 e2e).
- **Two-factor authentication for admin accounts** (Phase 6). TOTP (RFC 4226/6238) implemented directly against `node:crypto` (`domain/totp.util.ts`), no new dependency. `User.totpSecret`/`totpEnabledAt` + `TwoFactorChallenge` model (DATABASE.md §4.4, hash-only, single-use, 5-minute TTL — same shape as `PasswordResetToken`). `POST /auth/2fa/setup` (ADMIN) issues an AES-256-GCM-encrypted secret (`domain/secret-encryption.util.ts`) and an `otpauth://` URI; `POST /auth/2fa/enable` confirms it with a code before `totpEnabledAt` is set, so a typo during setup cannot lock the account out. `AuthService.login` returns `{ twoFactorRequired: true, challengeToken }` instead of a token pair once `totpEnabledAt` is set; `POST /auth/2fa/verify` (public) exchanges the challenge and a TOTP code for a real session. `POST /auth/2fa/disable` requires a currently valid code, not just the bearer token. 862 tests total (655 unit + 189 e2e).
- **Email verification** (Phase 6 — Hardening & Launch, opens the phase). `EmailVerificationToken` model, the same shape as `PasswordResetToken`: only the SHA-256 hash is stored, the raw token exists once in the outbound email, and issuing a new one invalidates any still-outstanding token. `AuthService.registerClient`/`registerMaster` call `EmailVerificationService.issue()` right after their transaction commits, so every new account is emailed a verification link without registration waiting on mail delivery. `POST /auth/verify-email` (public, single-use, `400 INVALID_VERIFICATION_TOKEN`) sets `User.emailVerifiedAt`; `POST /auth/resend-verification` (authenticated) re-issues a link, `409 EMAIL_ALREADY_VERIFIED` if already confirmed. Judgment call: `emailVerifiedAt` gates nothing else in v1 — no FR/SRS document specifies an enforcement rule, so none was invented; documented in `STATUS.md`. 828 tests total (649 unit + 183 e2e).

### Added
- **Load testing closes Phase 5.** `k6/simple-reads.js` (NFR-P-1: p95 ≤ 200ms for `/users/me`, a booking, the notification list, at 100 rps constant arrival rate), joining Phase 3's `k6/search.js`/`k6/availability.js`. `prisma/seed/scale.seed.ts` (`npm run seed:scale`) batch-seeds 50,000 masters with one service each via `createMany`, the dataset NFR-P-2's search benchmark needs and the dev seed never provided — a local/staging-only fixture, not reference data. Running k6 against a seeded stack remains a manual step, same as the two existing scripts, since neither k6 nor a scaled database is part of this repo's CI.
- **Prometheus metrics** (NFR-O-4, DEPLOYMENT.md §8). `GET /metrics`, a new `MetricsModule` (`src/shared/metrics`) registering a global `MetricsInterceptor` the same way `AuditModule` self-registers its own — records every request's method, matched route pattern (never the raw path, to keep label cardinality bounded) and status code into a `prom-client` counter and latency histogram, alongside Node's default process metrics. `@ApiAuth(ADMIN)`-protected like every other admin route, so a scrape config authenticates with a bearer token. DB connection-pool and scheduled-job-outcome gauges — also named in NFR-O-4 — are not implemented; they need instrumentation inside `PrismaModule` and each job respectively, out of scope for this pass. Admin broadcast notifications (`POST /admin/notifications/broadcast`) had already shipped with F-11 in Phase 4 and are only checked off in the tracking docs here. 819 tests total (640 unit + 179 e2e).
- **F-15 Admin dashboard** (FUNCTIONAL_REQUIREMENTS.md §11 FR-11.1, MODULES.md › AdminModule, closes Phase 5's feature list). `GET /admin/dashboard?from=&to=` — a new, table-less `AdminModule` sitting at the top of the dependency graph (ARCHITECTURE.md §4): it queries `PrismaService` directly rather than importing every feature module, since an aggregate report has no business rule to delegate to. Returns user counts by role plus a global blocked count, masters by approval status (an `approved`/`isActive:false` row is reported as `inactive`, distinct from `rejected`), bookings by status for the range (`REJECTED` folded into `cancelled` alongside the three `CANCELLED_BY_*` reasons — the API.md §12 response shape has no separate slot for it), completion/cancellation/acceptance rates, a `VISIBLE`-only review count and average rating, the top 10 categories by booking volume (grouped by `Booking.serviceId`, resolved to `Service.category` and merged), and a zero-filled daily series of bookings created/completed (`generate_series` LEFT JOINed against two `date_trunc('day', …)` aggregates in one raw query).
- `from`/`to` are independently optional (FR-11.1 gives no default): a missing bound resolves to a 30-day window anchored on whichever bound was given, or on `now` if neither was — a documented default (`domain/dashboard-range.util.ts`), the same kind of judgment call the booking-reminder job's timing was in Phase 4. The resolved span is capped at 366 days and reuses the existing `DATE_RANGE_TOO_LARGE` code (`schedule`'s precedent for a service-level, not DTO-level, range check) rather than registering a new one.
- Acceptance rate is computed from `Booking.acceptedAt IS NOT NULL`, not from the status bucket, so a booking accepted and later cancelled still counts as having been accepted — the two rates measure different things and would otherwise silently disagree with the displayed `cancelled` count.
- Unit tests for the pure range resolver/validator and `DashboardService` (rate math, zero-division guards, status bucketing, category folding/sorting/capping); `test/e2e/admin-dashboard.e2e-spec.ts` covers the empty-database shape, real counts from seeded users/masters, the `DATE_RANGE_TOO_LARGE` rejection, and the six-case authorization matrix.

### Fixed
- The daily-series raw query's `generate_series(...) AS day` produced `column reference "day" is ambiguous` once joined against two subqueries that alias their own grouping column `day` — caught before this reached a committed migration path by running the query directly against Postgres rather than trusting the Prisma type-check alone; fixed by aliasing the generated series as `series(day)` and qualifying every join/order reference.

### Added
- **F-14 Banners** (DATABASE.md §12, MODULES.md › BannersModule, Phase 5). `BannerPosition` enum (`HOME_TOP`/`HOME_MIDDLE`/`CATEGORY_TOP`) and `Banner` model, following the same admin-CRUD-plus-public-read shape as `CategoriesModule`: `POST|GET|PATCH|DELETE /admin/banners[/:id]` (`ADMIN`-only, each mutation wrapped in `@Audit()` with the pre-registered `BANNER_CREATED`/`BANNER_UPDATED`/`BANNER_DELETED` actions) and `GET /banners?position=` (public, unauthenticated). The public endpoint filters to `isActive` rows whose `[startsAt, endsAt]` window (either bound optional) covers the current instant — DATABASE.md §12's exact rule, expressed once as a pure predicate (`domain/active-window.util.ts`, exhaustively unit-tested: no bounds, one bound in either direction, both bounds, exact-boundary inclusivity) and mirrored as the equivalent Prisma `where` in `BannersService.listPublic`.
- `CreateBannerDto`/`UpdateBannerDto.imageKey` names the field after the literal FR-11.2 contract, but — matching the precedent `SendMessageDto.attachmentKeys` set in F-12 — its value is a confirmed `File` id (`FilePurpose.BANNER`), resolved and ownership-checked through `FilesService.getAttachable`, never a raw storage key a client could invent to probe another admin's upload. Replacing a banner's image on `PATCH` releases the old `File` via `FilesService.softDelete`, the same pattern `CategoriesService.update` uses for `iconFileId`.
- `startsAt`/`endsAt` are each independently optional with `endsAt` required after `startsAt` only when both are present in the same request. The shared `IsAfterField` validator treats a missing sibling as invalid (correct for the required pairs it already guards, e.g. `WorkingDayDto`), so a new `IsAfterFieldIfPresent` (`src/modules/banners/domain`) was added instead of reusing it as-is — same lexicographic comparison, but valid when the sibling is absent.
- `Banner` added to `SOFT_DELETABLE_MODELS` (`prisma/extensions/soft-delete.extension.ts`) so every read transparently excludes soft-deleted rows, and to the e2e `truncateAll` table list.
- Unit tests for `BannersService` (image resolution, admin pagination, active-window query shape, soft delete) and the domain predicates; e2e coverage in `test/e2e/banners.e2e-spec.ts` includes the six-case authorization matrix on every admin route and a public-read test proving only currently-active, position-matching banners are returned, ordered by `sortOrder`.

### Fixed

### Added
- **F-12 Chat** (DATABASE.md §9, MODULES.md › ChatModule, opens Phase 5). `Conversation`/`Message`/`MessageAttachment` models — `Conversation` unique on `(clientProfileId, masterProfileId)` (BR-60). `POST /conversations` is a find-or-create gated on a shared booking whose status is anything other than `EXPIRED` (documented in `STATUS.md` as the narrowest correct reading of "non-expired"), else `403 NO_SHARED_BOOKING`. `GET /conversations` is paginated, ordered by `lastMessageAt` DESC, with a per-conversation unread count (messages not sent by the caller with `readAt IS NULL`). `GET /conversations/:id/messages` is the first cursor-paginated endpoint in the codebase (`CursorPaginatedDto`/`ApiCursorPaginatedResponse`, new alongside the existing page/limit pattern), newest first, backed by `(conversationId, createdAt DESC)`. `POST /conversations/:id/messages` caps the body at 4000 characters via a service-level check (`422 MESSAGE_TOO_LONG`, a registered code distinct from generic `VALIDATION_FAILED`), resolves `attachmentKeys` as the caller's own confirmed `File` ids through `FilesService.getAttachable` (the same ownership-scoped pattern as `GET /files/:id/url`), and updates `Conversation.lastMessageAt`/`lastMessagePreview` in the same transaction as the message. `PATCH /conversations/:id/read` marks every unread message read. `DELETE /messages/:id` is a sender-side soft delete only — 404 for anyone else, including the other participant, per the ownership → 404 convention.
- `/chat` Socket.io namespace (`ChatGateway`): JWT verified in the handshake by reusing `JwtStrategy` (now exported from `AuthModule` alongside `JwtModule`) rather than duplicating secret/issuer/audience checks, so an expired, forged or since-blocked-account token is rejected the same way on both transports. Rooms are keyed by conversation id per `ARCHITECTURE.md` §7; the gateway is a broadcast-only relay of the `MessageSentEvent`/`MessagesReadEvent` `MessagesService` emits after commit — it never creates a `Message` itself. A `RedisIoAdapter` (`@socket.io/redis-adapter`, duplicating `RedisService`'s connection) fans events out across instances, wired in `main.ts` before `listen()`. The gateway is `@Public()` — the global `JwtAuthGuard`/`RolesGuard` are built for the HTTP `ExecutionContext` and do not understand a websocket one, so `handleConnection`'s own verification is this transport's equivalent.
- `NotificationsModule`'s `MessageNotificationsListener` reacts to `chat.message.sent` → `NotificationType.MESSAGE_RECEIVED`, following the same event-only pattern as the booking/review listeners; `ChatModule` never imports `NotificationsModule`.
- `GET /admin/conversations/:id/messages` — audited (`AuditAction.CONVERSATION_ACCESSED`) admin read. `USER_ROLES.md`/BR-63 describe this as restricted to a flagged dispute, but dispute arbitration has no in-app mechanism in v1 (`BACKLOG.md`); the route is reachable by any admin for any conversation and every call is audited, which is what makes that acceptable without a flag column that does not exist yet.
- `test/e2e/chat.e2e-spec.ts` proves BR-60 (a duplicate `POST /conversations` returns the existing row, not a second one), `NO_SHARED_BOOKING` enforcement (including the EXPIRED-only vs. CANCELLED distinction), the six-case authorization matrix on `GET /conversations/:id/messages`, and — using a real `socket.io-client` against the booted e2e app — that the `/chat` handshake rejects a missing/malformed token and that `message:new` reaches both participants but not a third party.

### Fixed
- `npx prisma migrate dev` for this feature proposed dropping `master_profiles.search_vector` — a generated column added by raw SQL in an earlier migration and deliberately absent from `schema.prisma`, which Prisma's schema diff cannot see and therefore treated as drift. The destructive `DROP COLUMN`/`DROP INDEX` was removed from the generated migration file by hand; `prisma migrate deploy` against a fresh database (as the e2e harness runs on every boot) confirms the corrected migration replays cleanly with the column intact.

### Added
- **F-09 Bookings** (DATABASE.md §7, MODULES.md › BookingsModule). `Booking`/`BookingStatusHistory` models plus a `bookings_no_overlap` GiST exclusion constraint (`EXCLUDE USING gist (master_profile_id WITH =, tstzrange(scheduled_at, ends_at) WITH &&) WHERE (status IN ('ACCEPTED','IN_PROGRESS') AND deleted_at IS NULL)`) and a `booking_number_seq` sequence the application formats into `UG-<year>-<padded>`. `POST /bookings` checks all six FR-7.1 pre-conditions in order (master approved/active, service active and owned, ≥2h lead time, slot inside computed availability, no client overlap, <5 open PENDING bookings) before writing a denormalised service/price snapshot. `BookingStateMachine` (`src/modules/bookings/domain`) is pure and stateless, reproducing FUNCTIONAL_REQUIREMENTS.md §7.1's transition table as data; it sits at 100% branch coverage via an exhaustive 9-status × 9-target × 4-actor cross product.
- `POST /bookings/:id/accept` runs at `SERIALIZABLE` with an application-level overlap re-check in addition to the exclusion constraint — the constraint is the real guarantee; the re-check exists to turn a genuine race into a documented `409 BOOKING_OVERLAP` rather than a raw 500 wherever possible. `reject`/`cancel` (client, master, admin)/`start`/`complete` each append an immutable `BookingStatusHistory` row in the same transaction as the state change and emit their domain event only after it commits. Cancelling an `ACCEPTED` booking within 3 hours of `scheduledAt` sets `isLateCancellation`.
- Progressive contact-detail disclosure: `BookingResponseDto` reveals the client's phone and full address to the master only once status reaches `ACCEPTED` — before that it exposes `addressDistrict` only. Enforced in the response projection, not by an ad hoc field omission, and covered by an explicit e2e assertion.
- `ExpirePendingBookingsJob` (every 10 minutes, FR-7.5) transitions overdue `PENDING` bookings to `EXPIRED` in batches of 100 using `FOR UPDATE SKIP LOCKED`, safe under concurrent runs or instances. `BookingReminderJob` — timing/lead time is a default proposed and applied per `CLAUDE.md` §3, since no FR/SRS document specifies this job the way FR-7.5 specifies the expiry job; see `booking.constants.ts` for the reasoning.
- `AvailabilityService` now subtracts real `ACCEPTED`/`IN_PROGRESS` bookings as busy intervals, replacing the `busyIntervals: []` placeholder Phase 3 left for this phase.
- **F-11 Notifications** (DATABASE.md §10, MODULES.md › NotificationsModule). `Notification` model; `GET /notifications` (paginated, `?isRead=`), `GET /notifications/unread-count`, `PATCH /notifications/:id/read`, `PATCH /notifications/read-all`, all strictly scoped to the caller. `POST /admin/notifications/broadcast` sends to a role or an explicit user-id list. Every notification is written by an `@OnEvent` listener reacting to a domain event — `BookingsModule`/`ReviewsModule`/`MastersModule` never call `NotificationsModule` directly, and `NotificationsModule` depends on nothing but `PrismaModule`. This also wires up `MASTER_MODERATION_EVENT`, emitted since Phase 2 with nothing listening until now.
- **F-10 Reviews** (DATABASE.md §8, MODULES.md › ReviewsModule). `Review`/`ReviewReply` models; `POST /reviews` is booking-gated (`COMPLETED` only, within 30 days of `completedAt`, one review per booking via a unique `bookingId`), `PATCH /reviews/:id` within a 24-hour edit window, `POST /reviews/:id/reply` (one per review), `GET /masters/:id/reviews` (public, visible only, with the `{1..5: count}` rating distribution), `POST/admin/reviews/:id/{hide,unhide}` (audited). `MasterProfile.ratingAverage`/`ratingCount` are recomputed from the current `VISIBLE` set inside the same transaction as every create/edit/hide/unhide, per DATABASE.md §3.3's denormalisation contract — never incrementally.
- Concurrency suite: a direct Prisma insert bypassing every service proves the exclusion constraint itself rejects an overlapping `ACCEPTED` booking; two concurrent `accept()` calls on overlapping bookings resolve to exactly one 200 and one `409 BOOKING_OVERLAP`; two concurrent review creations on the same booking resolve to exactly one 201 and one `409 REVIEW_ALREADY_EXISTS`, backed by `Review.bookingId`'s unique constraint.

### Fixed
- `test-app.factory.ts` now stops every registered cron job after boot (`SchedulerRegistry`). ### Added
- **F-07 Schedule** (DATABASE.md §6, MODULES.md › ScheduleModule). `WorkingDay` (weekly template) and `ScheduleException` (date override) models, each with a database `CHECK` enforcing `endTime > startTime` in addition to DTO validation. `PUT /masters/me/schedule` replaces the whole weekly set atomically and rejects an overlapping pair on the same weekday with `SCHEDULE_OVERLAP`; `POST/DELETE /masters/me/schedule/exceptions` manage day-offs and custom hours, rejecting a duplicate date with `EXCEPTION_ALREADY_EXISTS` and an incomplete/invalid non-day-off range with `INVALID_TIME_RANGE`.
- `AvailabilityCalculator` (`src/modules/schedule/domain`) is a pure function of (weekly rules, exceptions, busy intervals, now) — MODULES.md's own description of it — so it is unit-tested directly with no database. Timezone conversion (`zoned-time.ts`) uses only `Intl.DateTimeFormat` to compute a zone's UTC offset for a given instant; no date library was added (`CLAUDE.md` §5 requires asking first, and the guess-and-correct technique needs nothing else). `GET /masters/:id/availability` exposes it publicly, capped at 31 days via a dedicated `DATE_RANGE_TOO_LARGE` rather than the generic `VALIDATION_FAILED` a DTO-level check would have produced.
- No `Booking` model exists until Phase 4 (F-09), so `busyIntervals` is always `[]` today — the calculator's signature already accepts it, so wiring real bookings in later is additive, not a rewrite.
- **F-08 Search** (MODULES.md › SearchModule). - `AuditInterceptor`, registered globally, is a no-op for any route without `@Audit(action, entityType)` — adding it could not retroactively start auditing a route nobody decorated, and nothing does yet. `before` is the submitted request body and `after` the returned response, both redacted for `password`, `passwordHash`, `token`, `tokenHash`, `accessToken`, `refreshToken` and `resetToken`-shaped keys at any depth: a generic interceptor has no way to know which repository owns the decorated entity, so reading the database twice to recover prior state the owning service already loaded once was not worth the coupling.

- **F-05 Categories** (DATABASE.md §5.1, BR-20/21/22). `GET /categories` (cached in-process 5 min — Redis-shared caching is B-60) and `GET /categories/:slug` (with ancestors and one level of children) are public; `POST|PATCH|DELETE /admin/categories` are ADMIN-only and each mutation is `@Audit()`-decorated, the first real consumer of F-16. `slug` is immutable — absent from the update DTO entirely, not merely ignored. Reparenting recomputes `depth` for the whole subtree in one transaction, rejects a move that would exceed depth 3 (`CATEGORY_DEPTH_EXCEEDED`) or would parent a category under itself or its own descendant (`CATEGORY_INVALID_PARENT`, a new code — DATABASE.md's `AuditAction` enum had no dedicated value for this case). Deleting a category with children is blocked (`CATEGORY_IN_USE`); the equivalent check against active services lands with F-06, which is what creates the first service a category could reference.

- **F-02 Users.** `GET /users/me` returns the account with whichever profile the role implies, `PATCH /users/me` applies a partial update, and `DELETE /users/me` soft-deletes the account and revokes every session in one transaction — after which the email and phone are free to register again. `GET /cities` serves the public reference list.
- `passwordHash` is excluded **structurally** rather than filtered out: every read goes through a Prisma `select` that never names it, so the row has no such property and neither does its inferred type. A response mapper cannot leak a field that was never fetched.
- A profile field belonging to the other role — `displayName` sent by a client — is rejected with `422` naming the field, not silently dropped. Silent stripping is what `forbidNonWhitelisted` exists to prevent, and it should not reappear one layer down.

- **F-01 Authentication.** All nine `/auth` endpoints: registration for clients and masters, login, refresh, logout, logout-all, forgot-password, reset-password and password change. Access tokens are 15-minute HS256 JWTs carrying no PII; refresh tokens are opaque 512-bit values stored only as a SHA-256 hash, so a database dump yields no usable sessions.
- Refresh-token rotation with family tracking and reuse detection. Replaying a consumed token revokes every session in its family and returns `REFRESH_TOKEN_REUSED`; two concurrent refreshes of the same token leave exactly one successor, and the loser is *not* treated as reuse — revoking the family there would also revoke the token the winner just received.
- Login cannot be used to discover which addresses are registered: an unknown email and a wrong password return byte-identical bodies, and the unknown-email path burns a real bcrypt comparison against a dummy hash derived from the configured cost. Measured at 254ms versus 270ms against a running server. Account status is reported only *after* the password verifies, so `ACCOUNT_BLOCKED` cannot confirm an address either.
- `JwtStrategy` re-reads the account on every request, so a blocked or deleted user loses access immediately rather than whenever their token expires. `JwtAuthGuard` is global with `@Public()` as the only opt-out — forgetting a decorator locks an endpoint rather than opening it.
- Password reset stores only the token hash, issues one active link per user, and revokes **every** session on completion.
- `MailModule` behind a `MailProvider` interface, with SMTP delivery and bounded retry. Delivery never decides the outcome of the request that triggered it: `/auth/forgot-password` answers 202 either way, so relay behaviour cannot become an enumeration signal.
- Rate limits from `API.md` §13, keyed by IP.
- **F-13 Files.** `POST /files/presign` issues a short-lived upload URL, `POST /files/:id/confirm` verifies the stored object, and `GET /files/:id/url` signs a 15-minute read URL. Binaries never pass through the API process — the client PUTs directly to the object store, which is what keeps a 10 MB upload off the request path (`SECURITY.md` §2.7).
- Nothing a client declares at presign time is trusted. The MIME type and size are checked there only to fail fast and to bound what the signed URL will accept — `ContentLength` is signed into the URL, so the store itself rejects an oversized body rather than the API discovering it after the bandwidth is spent. A file becomes usable only at confirmation, which HEADs the object and reads its **real** content type and size; a mismatch deletes both the object and the row. Confirmation is idempotent, so a client retrying after a dropped response is not punished for it.
- The object key is built as `<prefix>/<userId>/<uuid><ext>` and never contains the name the client sent — only its extension, and only after being restricted to a short alphanumeric run. Object stores accept `../` in a key, which makes a key built from user input both a traversal and a content-type-confusion surface.

- `CleanupUnconfirmedFilesJob` reclaims two populations that otherwise leak storage indefinitely: presigns abandoned more than 24 hours ago, and files released by a replacement. It deletes the object before the row, so a failure between the two leaves a row to retry from rather than an orphan nothing points at, and reads through the **unfiltered** Prisma client — `File` is soft-deletable, so the default client would hide exactly the rows the job exists to collect.
- **`PATCH /users/me/avatar`** (FR-3.3, completing F-02). Attaches a file that is already confirmed and carries purpose `AVATAR`; the previous avatar is released for the cleanup job, so replacing a picture does not leave the old object paid for indefinitely. A file belonging to another user, or uploaded for another purpose, returns `404` rather than `403` — a distinguishable response makes an id probeable for existence.

The key is server-generated and returned only for correlation, while the id is the handle for the row carrying `isConfirmed` — the state the attach step exists to check. Accepting a key would mean resolving it to that row anyway, over a value the client is free to invent.

The password is only ever entered interactively and is not echoed; passing `--password` is refused with an explanation rather than quietly accepted, because an argv value is visible in `ps`, in shell history and in any CI log that echoes the command. Booting the application module would start the cron scheduler, the throttler and the global guards in a process that serves no requests — `admin:create` would begin running the hourly file-cleanup job as a side effect of creating an account.

- `GET /files/:id/url` is scoped to the uploader and returns `404` for anyone else's file. ### Fixed
- **Refresh-token reuse detection never fired.** Rotation marks the consumed row both `usedAt` and `revokedAt`, and the revoked check ran first — so replaying a stolen token returned `INVALID_REFRESH_TOKEN` and the family was never revoked. The scheme's entire security value is that a theft becomes detectable; it was silently absent. Found by replaying a token against a running server, fixed by ordering the reuse check first, and pinned by tests including one that holds whatever combination of flags is set.
- **Every named rate limiter applied to every route.** `@nestjs/throttler` runs all declared throttlers and `@Throttle` only overrides the one it names, so a registration was simultaneously counted against the forgot-password bucket and started returning 429 on the fourth attempt. - **Soft delete did not apply inside transactions.** `TransactionManager` started transactions from the base Prisma client, which hands the callback an unextended handle, so every read inside a transaction saw deleted rows. This was the one place `DATABASE.md` §1's guarantee silently did not hold, and the place it matters most: uniqueness checks and state reads happen inside transactions, so a soft-deleted account could have been treated as live. Transactions now run on the soft-delete-aware client. Confirmed against the running database before and after, and pinned by a regression test.
- `npm ci` failed inside the Docker build with `Missing: @emnapi/core@2.0.0-alpha.3 from lock file`. `package-lock.json` had been generated on Windows, where npm resolves the wasm32-wasi optional dependency subtree of `unrs-resolver` (reached via `eslint-import-resolver-typescript`) differently and never records the hoisted `@emnapi` packages that Linux needs. Regenerating the lock inside a `node:22-alpine` container produces a lock valid on both platforms. Regenerate it the same way after adding a dependency.

## Conventions

### Entry format

```markdown
## [1.2.0] — 2026-09-15

### Added
- `POST /bookings/:id/reschedule` — clients may move a booking once, ≥ 24 h before the slot. (#142)

### Fixed
- Availability computation dropped the final slot when a working day ended exactly on a slot boundary. (#151)

### Database
- Migration `20260915_add_booking_reschedule_count` — adds `bookings.reschedule_count` (nullable, backfilled to 0).

### Security
- Refresh token reuse now revokes the entire token family instead of the single token. (#149)
```

### Rules

1. **Every user-visible or contract-affecting change gets an entry.** Internal refactors that change no behaviour do not.
2. **Write for the consumer of the change**, not for the person who made it. "Clients may move a booking once" is useful; "refactored BookingService" is not.
3. **Database migrations always get an entry** under `Database`, naming the migration and stating whether it is backwards-compatible.
4. **Security fixes always get an entry** under `Security`, with enough detail for an operator to assess exposure and without enough detail to be a working exploit.
5. **Breaking changes** are called out explicitly with a `BREAKING:` prefix and a migration note. A breaking change to the public API requires a new API version, not just a changelog line.
6. Entries link to the pull request or issue.
7. `[Unreleased]` accumulates during a phase and is renamed to a version on release.

| Bump | When |
| --- | --- |
| **MAJOR** | Breaking change to the public API contract |
| **MINOR** | New backwards-compatible feature |
| **PATCH** | Backwards-compatible fix |
