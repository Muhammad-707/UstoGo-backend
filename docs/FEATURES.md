# Feature Catalogue — UstoGo Backend

**Version:** 1.0.0
**Last updated:** 2026-07-29

Each feature maps 1:1 to a NestJS feature module (`MODULES.md`) and to a roadmap phase (`ROADMAP.md`). Status values: `Planned` · `In progress` · `Done`.

---

## F-01 · Authentication & Session Management
**Module:** `auth` · **Phase:** 1 · **Status:** Planned

- Client and master self-registration
- Login with uniform failure responses
- JWT access token (15 min) + rotating refresh token (30 days)
- Refresh with reuse detection and family revocation
- Logout (single device) and logout-all
- Forgot / reset password by emailed single-use token
- Change password with session invalidation
- Rate limiting on all auth endpoints

**Depends on:** `users`, `prisma`, `config`, `mail`
**Key risks:** token rotation races under concurrent refresh — mitigated by a unique index on the token hash and a transactional consume-then-issue.

---

## F-02 · User & Profile Management
**Module:** `users` · **Phase:** 1 · **Status:** Planned

- Read and update own profile (role-aware payload)
- Avatar upload via presigned URL
- Account deactivation (soft delete + session revocation)
- City reference data
- Admin listing of users with filters

---

## F-03 · Master Profile & Onboarding
**Module:** `masters` · **Phase:** 2 · **Status:** Planned

- Extended professional profile: display name, bio, experience, service radius, timezone
- Category attachment / detachment
- Certificate upload, listing, deletion
- Submit and resubmit for review
- Public profile projection (aggregate rating, services, reviews, schedule summary)

---

## F-04 · Master Moderation
**Module:** `admin` (masters section) · **Phase:** 2 · **Status:** Planned

- Approve, reject with reason, activate, deactivate
- Readiness checks before approval (≥1 category, ≥1 active service)
- Moderation notifications
- Full audit trail of every decision

---

## F-05 · Category Catalogue
**Module:** `categories` · **Phase:** 2 · **Status:** Planned

- Public hierarchical tree, active only, cached
- Admin CRUD with depth limit 3 and leaf-only service attachment
- Slug uniqueness, immutable after creation
- Deactivation instead of deletion when in use

---

## F-06 · Service Catalogue
**Module:** `services` · **Phase:** 2 · **Status:** Planned

- Master-scoped CRUD
- Price types `FIXED`, `HOURLY`, `FROM`
- Duration in 15-minute increments, 15–1440 minutes
- Soft delete with a denormalised snapshot preserved on existing bookings

---

## F-07 · Availability & Scheduling
**Module:** `schedule` · **Phase:** 3 · **Status:** Planned

- Weekly working days, replaced atomically
- Date-specific exceptions (day off or altered window)
- Computed free-slot endpoint over a date range, service-duration aware
- Timezone-correct expansion, UTC output

---

## F-08 · Master Discovery
**Module:** `search` · **Phase:** 3 · **Status:** Planned

- Free-text search over display name, bio and service titles (PostgreSQL full-text with a GIN index)
- Filters: category, city, minimum rating, price range, availability on a date, has-certificates
- Sorting: rating, review count, price ascending/descending, newest
- Pagination with total count
- Only approved, active, non-deleted masters are ever returned

---

## F-09 · Booking Lifecycle
**Module:** `bookings` · **Phase:** 4 · **Status:** Planned

- Creation with six ordered pre-condition checks
- Explicit state machine with a single authoritative transition table
- Transactional acceptance preventing overlaps
- Reject / cancel with mandatory reasons, late-cancellation flagging
- Start and complete
- Append-only status history
- Scheduled expiry of stale pending requests
- Progressive disclosure of client contact details

---

## F-10 · Reviews & Ratings
**Module:** `reviews` · **Phase:** 4 · **Status:** Planned

- Booking-gated creation, one per booking, 30-day window
- 24-hour edit window
- Master reply, one per review
- Admin hide / unhide with aggregate recomputation
- Denormalised `ratingAverage` / `ratingCount` maintained transactionally
- Public listing with rating distribution

---

## F-11 · Notifications
**Module:** `notifications` · **Phase:** 4 · **Status:** Planned

- Persisted, per-user, typed notifications with structured payloads
- Generated by domain events, never by controllers
- List, filter by read state, unread count, mark one/all read
- Admin broadcast to a role or a user

---

## F-12 · Messaging
**Module:** `chat` · **Phase:** 5 · **Status:** Planned (contract frozen in v1 docs)

- Conversation per (client, master) pair, gated on a shared booking
- Cursor-paginated message history
- REST send/read, functionally complete without WebSockets
- Socket.io `/chat` namespace with JWT handshake as a latency optimisation
- Sender-side soft delete of own messages

---

## F-13 · File Storage
**Module:** `files` · **Phase:** 1 · **Status:** Planned

- Presigned upload URLs with MIME and size constraints
- Server-side verification of the uploaded object before persistence
- Presigned, time-limited read URLs
- Provider behind a `StorageProvider` interface (S3 in production, MinIO locally)
- Orphan cleanup job

---

## F-14 · Banners
**Module:** `banners` · **Phase:** 5 · **Status:** Planned

- Admin CRUD with position, sort order and an active time window
- Public read filtered to the current instant

---

## F-15 · Admin Dashboard
**Module:** `admin` · **Phase:** 5 · **Status:** Planned

- Counts by role, status and approval state
- Booking funnel and status distribution over a date range
- Completion and cancellation rates
- Rating and review volume
- Top categories by booking volume
- Daily time series

---

## F-16 · Audit Log
**Module:** `audit` · **Phase:** 2 · **Status:** Planned

- Append-only records of every privileged mutation
- Before/after diff with sensitive fields redacted
- Written by an interceptor, not by hand in each service
- Admin-only, filterable read endpoint

---

## F-17 · Platform & Cross-cutting
**Modules:** `common`, `config`, `prisma`, `health`, `logger` · **Phase:** 1 · **Status:** Planned

- Boot-time environment schema validation
- Global validation pipe, exception filter, serialisation interceptor
- Request id middleware and structured logging
- Prisma soft-delete middleware
- Health and readiness endpoints
- Swagger generation with role-grouped tags
- Global and per-route rate limiting

## Feature Dependency Order

```
F-17 platform
  └─ F-01 auth ── F-02 users ── F-13 files
        └─ F-16 audit
              └─ F-05 categories ── F-03 masters ── F-04 moderation
                    └─ F-06 services
                          └─ F-07 schedule ── F-08 search
                                └─ F-09 bookings
                                      ├─ F-10 reviews
                                      ├─ F-11 notifications
                                      └─ F-12 chat
                                            └─ F-14 banners ── F-15 dashboard
```

A feature is only started when every feature it depends on is `Done`. This ordering is the contract behind the "one feature completely, then the next" rule in `PROJECT_RULES.md`.
